The answer to the owner's question first: yes, the 2026-09-22 amendment to spec 01 broke its own rule. Line 103 ("call enabled packs' after-write functions (guarded)") runs pack code inside the clinician's transaction, under the patient lock; no guard bounds a sleep, a lock wait or a raise loop, and test B1 cannot pass with it. The after-write *mechanism* (packs react to finished entries, may hold a request, never on rebuild) stands; the *call site* does not. It moves to a queue (`pack_calls`) and a runner that acts after the commit. The updater of a pack's own types stays inside the write, hardened. Everything below is that change plus the hardening the break-tests demanded. Line numbers refer to spec/01-record.md as of today.

**1. Status line (line 3).** Remove: "amended 2026-09-22: after-write functions added; the record carries no money". Add: "amended 2026-09-22 (spec 02): after-write reactions run through `pack_calls` after the commit, never inside `write_entry`; the record carries no money; access, users and settings are spec 02". Why: the amendment's call site is withdrawn and the reader must know where the organization half lives.

**2. `write_entry` sequence (lines 102–105).** Remove: "→ `change_request` once → call enabled packs' after-write functions (guarded) → signal. A retry with the same id returns the stored row, changes nothing, and calls no after-write function." Add: "→ `change_request` once → insert one `pack_calls` row per pack that is on for the organization, is called after write, and did not itself write the entry → signal. A retry with the same id returns the stored row and changes nothing; a rebuild and a step insert no `pack_calls` row. No pack code runs in `write_entry` except the updater of the entry's own type, and that updater is called only after a catalog check that it is a `security definer` function owned by its pack's role." Why: B1; rule 5 of spec 02. Appendix step 7 gains the insert; step 6 gains the definer check.

**3. Table row "Outside the record" (line 39).** Remove: "users · read-audit · `pack_failures`". Add: "`users` · `record_reads` · `settings_changes` · `pack_calls`". Why: the tables now have names and shapes (spec 02).

**4. Table row "Settings" (line 38).** Add at the end: "· `packs` · `department_types` · `served_departments` · `service_field_ranges` · `roles` · `actions` (spec 02)". Why: same kind, same rule, new tables. Row "Derived" (line 37): "pack tables" → "pack lists (`<pack>.<list>`)". Why: a pack's charges are not derived; only its updater-kept lists are.

**5. The rest block (lines 82–83).** Remove: "pack_after_write  pack · function_name (at most one per pack)" and "pack_failures   id · pack · entry_id · error_text · failed_at · retried_at". Add: "packs           key · name · is_called_after_write" and "pack_calls      pack · entry_id · organization_id · recorded_at · tries · tried_at · error_text    pk (pack, entry_id)". Why: a function name executed from a table is a door; `<pack>.after_write` is the contract and CI checks it exists; the row is the work, not the failure.

**6. Reads (line 97).** Remove: "read_to_review". Add: "read_to_review(organization_id, department_id) · read_entry_file(entry_id, position)". Why: the department owns unreviewed results after a doctor leaves (second partial index `(from_department_id, review_needed_at) WHERE review_needed_at IS NOT NULL`); files are reached only through a gated 60-second signed URL.

**7. Gates (line 98).** Remove: "require_access(organization_id, action, patient_id)". Add: "require_access(organization_id, action, patient_id, department_id) → the caller's users.id". Why: rights are per department; the department comes from the row being touched, like the organization. Appendix line 297 the same, plus: "`require_access` raises `unknown_action` for a key absent from `actions` and runs `require_pack` when the action belongs to a pack."

**8. Packs paragraph (lines 112–117).** Line 114: "a practice switches packs on" → "an organization switches packs on". Add after line 117: "A pack is a schema named by its key, owned by a NOLOGIN role `pack_<key>`; every function and table it ships is owned by that role and every function is `security definer` with `search_path` pinned; the role holds EXECUTE on the funnels and the public read and mark functions and nothing on any core table (spec 02)." Why: the boundary is now one Postgres enforces, and spec 01's "may never alter a core table" becomes a grant rather than a sentence.

**9. The packs table (lines 121–128).** Row *Named by*: "`pack_after_write (pack, function_name)` → `<pack>_after_write(entry)`" → "`packs.is_called_after_write` → `<pack>.after_write(entry)`". Row *Runs*: "once, after the write; **never on rebuild**" → "after the write has committed, in its own transaction, as the pack's own user (`users.kind = 'pack'`); at least once; **never on rebuild**". Row *If it fails*: "the write still succeeds; the failure is logged in `pack_failures` for the pack to retry" → "the write is unaffected; the failure is the `pack_calls` row's `error_text`, retried with back-off, parked after five tries and shown on the Organization page". Row *If it fails*, updater column: add "(a pack updater fails writes of that pack's own types only; `rebuild_record` isolates it)". Add a row *Is*: updater "a pure function: O(rows), no waits, no clock" · after-write "idempotent on `entry_id`; makes the pack's data match the entry as it is at call time". Why: the contract that makes order and retries irrelevant (B4, B5).

**10. The hold sentence (lines 130–132).** Remove: "They may call `mark_step` — that is how a billing pack holds a request until it is paid." Add: "They may call `mark_step` — that is how a billing pack holds a request (`sent` → `held`) a few seconds after it is sent; `mark_step` is compare-and-set, so a request already started stays started and the charge stays unpaid. A pack reacts to entries only, never to steps." Why: the hold is asynchronous by design; the race is bounded and stated.

**11. The boundary sentence (lines 136–137).** Remove: "Data flows one way: packs read the record; the record never reads a pack." Add: "Control and data flow one way: packs read the record; the record never reads a pack and never runs one, except the updater of a pack's own entry types inside that pack's own writes." Why: this is the rule the amendment broke; it is now true in control flow, not only in data flow.

**12. Naming (lines 144–145).** Add to Words: "organization · site · section · role · action · user · hold". Add to the vocabulary (appendix d): `held`. Why: spec 02's words used in spec 01 sentences.

**13. Enum (appendix lines 252–254).** `request_step` core values gain `held`; add: "`sent` is a legal target only from `held`." Why: a hold is core state that the record must fold; only a release may re-enter `sent`.

**14. Invariant 6, composite tenant foreign keys (appendix lines 323–327).** Add: "entries `(organization_id, department_id)`, `(organization_id, author_id)`, `(organization_id, responsible_id)` → departments / users; requests `(organization_id, assignee_id)` → users; request_steps `(organization_id, actor_id)` → users". Why: the per-parameter cross-organization matrix (S8) found `assignee_id`, `author_id` and `department_id` uncovered.

**15. Invariant 9, lock and clock (appendix lines 330–332).** Add: "EXECUTE on `pg_advisory_*` is revoked from PUBLIC and held by the core owner, so no pack can take the patient lock; on a host that refuses the revoke, CI's pack-body scan and the runner's 5 s timeout are the guard." Why: S3.

**16. Invariant 14, access (appendix lines 349–352).** Remove: "Every public function is `security definer set search_path = ''` and starts with `require_access(…)`." Add: "Every function in `core`, `public` and every pack schema is `security definer` with `search_path` pinned; every table and private function lives in schema `core`, `public` holds only callable functions, and default EXECUTE to PUBLIC is revoked in every schema. Every public core function starts with `require_access(…)`; when the caller is a pack role, `core.write_entry` and the step path of `core.change_request` run `require_access` themselves." Why: S2, S15, S16: ownership without `security definer` is no boundary; a pack wrapper that forgets its gate is still refused.

**17. Reads (appendix line 288).** Remove: "Every read function is `STABLE`." Add: "Every read function is `STABLE` except `read_record`, which inserts the `record_reads` row; the other record reads raise `record_not_open` without one in the last 12 hours, for users of kind `staff`, `patient` and `proxy`; machines, packs and importers read without opening and without a row." Why: the read audit is the open (O21).

**18. Updaters (appendix line 195).** Add after "It does not call `now()`, read settings or raise.": "It runs under the patient lock, so it is O(rows) with no waits. A pack updater that raises fails writes of that pack's own types only." Why: X1.

**19. `rebuild_record` (appendix line 300).** Add: "`rebuild_record` replays each list inside its own exception block (a savepoint per list) and reports the failing list by name in its counts, so a raising pack list leaves that pack's rows stale and every core list rebuilt." Why: X3 (breaks otherwise: merge and rebuild of any patient carrying a hostile-type entry would fail as a whole).

**20. Machine writes (appendix line 265 and invariant list).** Add: "When the author is a users row of kind `machine`, `write_entry` refuses an entry that is not a reply to an open request whose `to_department_id` is the department the machine holds its action in, unless it is a draft." Why: S13; a stolen analyser key is confined to requests already sent to that lab.

**21. Test 21 (appendix lines 366–368).** Remove: "A member of organization B calls every public function with organization A's fixture ids. Every such call must raise." Add: "For every function in `pg_proc` in schema `public`, enumerated at run time (pack wrappers included), and for every id parameter, array elements included, a member of organization B substitutes B's id of the same kind among A's ids; every such call must raise." Why: S8, S18: one call per function misses `assignee_id`, foreign codes, foreign roles, one foreign array element.

**22. Realtime (appendix lines 303–307).** Add: "Signals go on private channels with one RLS policy on `realtime.messages` (the membership InitPlan), so a retired user's open socket receives nothing." Why: S9.

Appendix wording, non-normative.** `services.result_type` → `reply_type`; `services.section` → `section_name`; `departments.site` → `site_name`, `contact` → `contact_text`; `lab_mark_collected` → `laboratory_mark_collected`; "A NULL `department_id` means the requester chooses the destination. Why: spec 02 names.
